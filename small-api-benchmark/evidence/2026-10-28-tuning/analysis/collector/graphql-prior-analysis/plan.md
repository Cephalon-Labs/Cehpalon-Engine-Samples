# GraphQL collector tuning diagnostic plan

Scope: collector instrumentation only. Keep all public business handlers, validation, fixed offered schedule, 80/15/5 mix, one-second deadlines, 128 outstanding cap, payloads, TLS behavior and error accounting unchanged for both variants. No latency floors, smoothing, outlier removal, threshold changes or selected replacement of prior runs.

Observed evidence: the prior slow Engine GraphQL run02 has p95 0.480505 ms, sent-to-completed p95 0.474793 ms and queue p95 0.005616 ms. Other Engine runs have p95 0.343007–0.382131 ms and queue p95 around0.0037–0.0044ms. Thus admission queue delay is not demonstrated to be the primary reason for the failed CV. Sent-to-completed includes collector continuation/validation work, not only server latency. Server allocations/CPU/GC vary; the existing data does not prove a single cause.

Code evidence: every completed row currently enters both ConcurrentBag and an unbounded Channel. A Task.Run consumer serializes an object array and gzip-compresses it while the offered schedule and HTTP continuations run on the collector's two assigned CPUs. Task.Run uses the shared ThreadPool (Microsoft primary API documentation: https://learn.microsoft.com/en-us/dotnet/api/system.threading.tasks.task.run). This is avoidable in-window instrumentation work, independently of the unproven CV cause.

Proposed bounded change: preallocate an indexed Observation array before the phase; record each offered index exactly once with atomic duplicate rejection. Preserve every timestamp/status/error/drop. Join admitted requests, persist every observed row with the identical schema after the phase, and validate complete index conservation. Keep the existing initial/final server metrics bracket including the flush; explicitly document this post-phase persistence interval. Managed exceptions join pending work and flush partial observations before failing; abrupt process termination cannot guarantee buffered raw retention and remains an invalid attempt. The scheduler's SpinWait/Task.Delay behavior stays unchanged because current data does not establish it as the dominant cause.

Offline checks: compile the actual project; validate indexing/duplicates/missing rows and compare decompressed raw row fields against the prior serializer using synthetic observations; verify payload-manifest generation remains unchanged. A short traffic trial requires a root-assigned isolated slot. Any accepted source change requires the whole unchanged protocol, not a selective rerun of the previous slow value.

## Accepted metrics-boundary correction after peer review

The first deferred-persistence draft retained the old Phase-inclusive server metrics bracket. Review correctly identified that flushing the entire gzip after requests could add a materially longer idle interval. Final measured server metrics are now captured immediately after the request join, before raw persistence, with a bounded ten-second control request; faults are recorded and cannot bypass the finally flush. This is an explicit measurement-boundary correction applied identically to both variants, requiring a complete new protocol. Raw per-request timestamps and all numerical budgets remain unchanged.

Cheap collector snapshots bracket the offered schedule/request join and exclude the server completion-metrics request and persistence. They record CPU, approximate allocated bytes, GC counts and ThreadPool counts with the phase start/completion ticks. TLS observations include the post-handshake PlaintextStreamFilter timestamp and Stopwatch frequency. These diagnostic observations do not establish a root cause or prove that variance improved. Observation references are preallocated, while each Observation record still allocates.
