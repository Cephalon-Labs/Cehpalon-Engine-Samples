# ADR0024 exact-source task ordering review

Read-only offline source review, 2026-11-01. No targets, SDK builds, captures, benchmark runs, host configuration edits or remote writes. Six official pinned source files were fetched with HTTP200 and retained with URL/byte/SHA256 provenance. Runtime VMR5254d8bcf59917edc1e1abc33bdf2442b77b1c70 and Roslyn8edf7bcd4f1594c3d68a6a567469f41dbd33dd1b are the previously observed revisions. This review does not attest loaded binaries or prove every captured callsite.

## Literal event observations and limits

1. Schedule is an instrumentation point before scheduler insertion. TaskScheduler.cs224-231 calls FireTaskScheduledIfNeeded before QueueTask. The default scheduler's ThreadPoolTaskScheduler.cs43-58 subsequently starts a dedicated LongRunning thread or inserts a ThreadPool work item. TryRunInline165-190 also emits schedule if needed before direct inline execution. Schedule-before-start therefore neither proves actual queue residence nor measures OS runnable-to-running delay. It includes event-write, scheduler/prelude and any intervening work. ThreadPool/task scheduler queues and kernel runqueues are different mechanisms.

2. Start is an execution-telemetry point before the delegate, after some executor work. Task.cs2427-2434 sets DelegateInvoked and checks cancellation before ExecuteWithThreadLocal emits TaskStarted2470/2472. That function subsequently installs TLS2480 and invokes InnerInvoke2489 or ExecutionContext dispatch2496/2500. Thus executor work precedes the event and delegate/context work follows it. TaskStarted is not a thread dequeue, first CPU instruction, delegate entry or first useful Roslyn instruction.

3. Complete is emitted after the executor's Finish call, not at a universal logical completion instant. Task.cs2513 invokes Finish(true); finally restores task TLS2517 and emits TaskCompleted2524/2526. For ordinary no-attached-child completion, FinishStageTwo publishes terminal state2245, signals2252 and runs FinishStageThree2257/continuations2287 before event9. Another thread may finish its wait while this executor is still running cleanup, continuations or delayed telemetry. For attached-child cases, FinishSlow2155-2175 may instead return with WaitingOnChildren before terminal completion. Therefore event9 can also precede eventual logical Task.IsCompleted in that family. These are source-supported possibilities, not claims about the observed selected tasks. Task.Run uses DenyChildAttach, but a method-context point alone does not prove the exact direct Task.Run callsite; keep option/context facts separate.

4. Event8-to-event9 elapsed is not delegate-only compilation time, CPU, work amount or uninterrupted execution. It may include context setup, exception processing, logical completion/continuation work, preemption, nested work and telemetry. Native event headers identify emitters at event points; no permanent ThreadPool ownership or native lifetime follows. Schedule destination scheduler identity and start/complete ambient-origin scheduler context retain distinct meanings.

## Wait ordering and races

TaskAwaiter.cs104-106 only calls InternalWait for an incomplete task on the relevant slow path. InternalWaitCore Task.cs3125-3129 checks completion again and returns without TaskWait events if already complete. This fast path means no wait event is not a zero-delay observation or a complete count of all GetResult joins.

If that IsCompleted read sees false, TaskWaitBegin10 is emitted only later at3138. In between, another thread may publish terminal state, run Finish and emit TaskCompleted9. Consequently **TaskCompleted-before-WaitBegin is legal**, even for ordinary no-attached-child Task.Run: a race after the false completion check is enough. Do not reject this order or label the waiter as performing redundant avoidable Engine work.

Conversely **WaitEnd-before-TaskCompleted is legal**: completion publication/signalling can release the waiter before the executor reaches its telemetry in finally. The wait interval is not necessarily contained inside TaskStarted-to-TaskCompleted, and event9 need not lie inside it. Generic API histories can also wait on an unstarted task that is scheduled later, so TaskWaitBegin-before-TaskScheduled is not universally invalid. A validated narrower Roslyn Task.Run path may imply additional program order, but method-point co-observation alone does not establish that path.

InternalWaitCore3153-3155 attempts inline execution for an infinite noncancelable wait; otherwise3159-3162 enters SpinThenBlockingWait. That method first SpinWait3214, may transfer local work to a global queue3233, register a completion action3238 and then call a managed reset-event wait3245. Completion can occur during spinning or registration. TaskWaitEnd3173/3177 occurs after these paths. TaskWait duration therefore spans some combination of prelude, inline execution, spinning, synchronization, blocking and caller re-scheduling; it is not a blocking, scheduling or GC-pause duration. Exceptions/cancellation/timeouts and missing history require explicit uncertainty, not fabricated end events.

## Roslyn correspondence and selection limits

Pinned MethodCompiler.cs329-341 pops tasks and calls GetAwaiter().GetResult. Concurrent named-type compilation424-425 obtains a Task.Run result then pushes it onto the stack; CompileNamedTypeAsync435-447 wraps CompileNamedType in the task. The comment45-57 describes flattened fork/join without parent-child dependency and LIFO tracking intended to improve chances of inlining. Work can finish before being pushed or popped, and completed GetResult calls may produce no TPL wait. Therefore selected TaskWait records do not enumerate all WaitForWorkers joins, and a direct-callsite claim remains false absent stronger evidence. Nested/inlined method frames retain the previous ADR0023 ambiguity limits.

## Timestamp handling for the new offline analyzer

Use exact retained timestamp values for literal before/after/equal classification. A same-value timestamp pair is a tie: parser raw record index, arrival/file order, PID, TID or a sorting tiebreak does not establish cross-thread temporal order. Source code may support specific program-order possibilities, but it cannot restore elapsed duration below retained timestamp precision or resolve which interleaving occurred. Zero timestamp difference is not zero work, zero blocking or no queue delay. Preserve ties explicitly.

Do not subtract event gaps into exclusive cause budgets, filter tied/raced cases, turn absent events into zeros, or reinterpret event7-to8 as queue/runqueue time. Output should use literal labels such as start_event_before_wait_begin / equal / after and complete_event_before_wait_begin / equal / after, with blocked_time, CPU, runqueue_delay, GC_pause and direct_callsite_proven left null/false. Include observed source option facts separately if available. No current source observation justifies an Engine patch, altered concurrency/GC or original benchmark rerun.
